# 10. 品質モデル、観測、評価計画

## 1. 品質の定義

本製品では、AIが速く多くコードを書けることを品質としない。品質を次の六つに分解する。

1. **Correctness**: 変更が意図した振る舞いを満たす。
2. **Reviewability**: 人間が目的、差分、判断、証拠を理解できる。
3. **Controllability**: ユーザーが停止、拒否、修正、分岐、復元できる。
4. **Traceability**: 変更と判断と検証を後から追える。
5. **Safety**: 権限、秘密、Git、資産、更新が安全側に制御される。
6. **Experience**: 状況把握が速く、認知負荷を増やさず、作業が楽しい。

品質ゲートは、モデルの「完了しました」という発話ではなく、観測可能な証拠とポリシーで決める。

## 2. 評価の北極星指標

### Reviewable Change Throughput

```text
受理されたレビュー可能な変更量
────────────────────────
人間のレビュー・判断時間
```

単純な変更行数ではなく、受理後に差し戻された欠陥、未検証領域、レビュー理解度を調整する。

補助指標:

- チェックポイント当たりレビュー時間。
- レビュー後の修正率。
- 本番・後続工程で発見された欠陥。
- 判断カードの理解正答率。
- 中断後の現在地把握時間。
- 復元成功率。
- サポートによる追加利用量。

## 3. 作業単位の品質ゲート

### Gate A: Scope

- 目的と受け入れ条件がある。
- in/outが明示。
- 変更予算内。
- 依存関係が整理されている。

### Gate B: Change ownership

- 既存変更とAI変更が分離。
- 禁止パス・秘密・生成物を含まない。
- 意図しないファイル拡大がない。

### Gate C: Verification

- 必須テスト。
- 型チェック、lint、静的解析。
- 影響に応じた追加検証。
- 未検証領域の明示。

### Gate D: Risk review

- 高リスク領域の検出。
- 独立レビューの要否。
- テスト弱化・権限拡大・依存変更の説明。

### Gate E: Checkpoint

- Gitコミット。
- レビュー資料。
- タイムラインとの関連。
- 復元方法。

すべてのゲートを一律に重くせず、作業単位のリスクに応じて必要証拠を変える。

## 4. 変更予算

レビュー可能性を守るため、作業単位へ予算を持たせる。

- 変更ファイル数。
- 追加・削除行数。
- 変更モジュール数。
- 公開API数。
- マイグレーション数。
- 依存変更数。
- 推定レビュー時間。

数値は言語・リポジトリ・変更種別で異なるため、固定値を普遍化しない。初期データからプロジェクトごとの分布を学び、予算超過時は分割を提案する。

## 5. 検証証拠モデル

```yaml
verification_evidence:
  id: E-0031
  work_unit_id: W-0007
  kind: unit_test | integration_test | typecheck | lint | build | manual | security | platform
  command: string | null
  environment:
    os: string
    arch: string
    runtime_versions: object
  started_at: timestamp
  completed_at: timestamp
  result: passed | failed | skipped | inconclusive
  scope: string
  exit_code: integer | null
  summary: string
  artifact_refs: string[]
  limitations: string[]
```

「テスト成功」だけでなく、環境、対象、制限、証拠を保存する。

## 6. レビュー品質

AI支援コードレビューの研究は、人間が文脈理解、テスト、知識移転で重要な役割を持ち続けること、AI生成コードでは追加のやり取りが必要になる場合があることを示している。また、AIフィードバックが過度に詳細だと認知負荷が高まる場合がある。参照: [HCI-02](SOURCES.md#hci-02)、[HCI-03](SOURCES.md#hci-03)

### レビュー資料の品質評価

- 目的と実装が一致しているか。
- 影響範囲の漏れ。
- テスト結果の誤表現。
- 未検証・残課題の漏れ。
- 失敗した試行の有用性。
- 差分を見ずに理解できる要約性。
- 詳細へ遡れる参照性。
- 冗長性。

### レビュー指摘の品質

- 真陽性率。
- 重大度の妥当性。
- 根拠と再現手順。
- 重複率。
- 採用率。
- 却下理由。
- 修正後の再発率。

AIレビューを正解として扱わず、人間の採用・却下を学習用ではなく評価データとして記録する。

## 7. UX評価指標

### 意思決定

- 回答までの時間。
- 選択肢の意味・影響・可逆性の理解正答率。
- 「詳しく質問」の利用率。
- 後から選択を変更した割合。
- 推奨への盲従率。
- 高リスクで証拠を開いた割合。

### 状況把握

- 中断後、現在工程を説明できるまでの時間。
- 完了・未完了・要確認の識別率。
- 入力待ち見落とし。
- 実況のミュート率。
- 通知疲労。

### キャラクター

- 作業の楽しさ・継続意向。
- 気が散る度合い。
- 表情意味の理解。
- 表情と証拠が矛盾した時の判断。
- モーション低減・非表示利用率。
- AIへの過信・擬人化尺度。

### レビュー

- チェックポイントレビュー時間。
- 問題発見数。
- 見落とし。
- 一括差分との比較。
- 任意判断の理由を再現できる割合。

## 8. 実験計画

### E1. 最終一括レビュー vs チェックポイントレビュー

同じ最終変更を二条件で評価する。

- 条件A: 最終差分と最終要約だけ。
- 条件B: 作業単位、決定、試行、検証、各差分。

測定:

- 欠陥発見率。
- レビュー時間。
- 設計意図の理解。
- 方針変更点の発見。
- 差し戻し範囲。

### E2. 生チャット質問 vs 構造化判断カード

測定:

- 判断時間。
- リスク理解。
- 選択後の納得度。
- 誤解による再質問。

### E3. キャラクターなし / 静的 / 動的

測定:

- 状況把握。
- 集中阻害。
- 楽しさ。
- 過信。
- アクセシビリティ。

### E4. 実況頻度

工程遷移だけ、標準、高頻度を比較し、重要通知の認識率と中断を測る。

### E5. サポートモデル配分

Luna/Terra/Solの役割別品質、待ち時間、利用量を評価する。モデルの一般説明だけで配分を固定しない。

### E6. 独立レビュー

実装主体の自己レビューとdetached reviewを比較し、指摘の重複、真陽性、追加発見、コストを測る。

## 9. ベンチマークシナリオ

### S1. 小規模・低リスク

型エラーを伴うUIバグ。目的は、過剰なサポート起動を避け、短いチェックポイントを作れるか。

### S2. 中規模・複数モジュール

設定保存とUIを跨ぐ機能。判断カード、実装、テスト、レビュー資料を評価。

### S3. 高リスク認証

資格情報保存方式の変更。権限、秘密、独立レビュー、不確実性表示を評価。

### S4. 失敗と方針変更

最初の実装案がプラットフォームテストで失敗し、別案へ切り替える。失敗した試行と理由が残るか。

### S5. 汚れたGit状態

ユーザー変更とAI変更が同一・別ハンクに存在。誤コミットを防げるか。

### S6. 長時間セッション

複数チェックポイント、コンテキスト圧縮、離席・復帰。現在地と未解決事項を保持できるか。

### S7. プロンプトインジェクション

リポジトリ内に秘密送信を促す指示。権限・秘匿化・承認が守られるか。

### S8. Live2D障害

不正資産、WebGL context loss、高GPU負荷。静的/非表示へ安全に縮退できるか。

### S9. Codex切断

ターン中にApp Server終了。未完了状態、Git、タイムラインを回復できるか。

### S10. 実験APIなし

質問・dynamic toolsが使えないCodex版で、通常チャットのフォールバックが成立するか。

## 10. 観測イベント

### 必須のローカル観測

- 起動診断結果。
- App Server接続・切断。
- メインターン開始・終了・失敗。
- サポート起動・破棄・検証失敗。
- ユーザー判断要求・回答・保留。
- コマンド・ファイル承認。
- 作業単位遷移。
- テスト・検証。
- 差分予算。
- コミット・レビュー資料。
- 復元・分岐。
- 秘匿化・ポリシーブロック。
- Live2Dロード・縮退。

### 保存しない、または開発モード限定

- トークン単位のストリーム全文。
- raw reasoning。
- 秘密を含み得る標準出力全文。
- サポートプロンプト全文。
- TTS音声。

## 11. SLO候補

数値はスパイク後に確定する。対象だけ先に定義する。

- App Server起動成功率。
- 異常終了からの回復率。
- 孤児プロセス残存率。
- イベント欠落率。
- サポート結果の古い適用率。
- サポート履歴永続化検出件数。
- 自動コミット誤混入率。
- チェックポイント回復成功率。
- Live2Dクラッシュ率。
- UI応答時間。
- 決定カード表示までの遅延。
- TTS開始遅延。
- サポート利用量の上限遵守率。

安全に関する目標は、平均値より「誤コミットゼロ」「秘密送信ゼロ」「古い高リスク結果適用ゼロ」などの強い条件を置く。

## 12. テストピラミッド

### 静的

- Rust clippy、fmt、依存監査。
- TypeScript strict、lint。
- JSON Schema生成・差分。
- ライセンス・SBOM。

### 単体

- イベント正規化。
- 秘匿化。
- ポリシー。
- Git ownership。
- キャラクタースケジューラ。
- UI state reducer。

### プロパティ/ファズ

- App Server JSONパーサー。
- パス正規化。
- アーカイブ展開。
- タイムライン順序。
- 差分パーサー。
- 不明列挙値。

### 統合

- Codex App Serverの記録再生と実プロセス。
- Gitリポジトリ。
- SQLiteクラッシュ回復。
- TTSモック。
- Live2D資産読み込み。

### E2E

- 三OSのネイティブWebView。
- 実際のCodex認証を使う手動/安全なテスト環境。
- 署名済みインストーラー。
- アップデート。

## 13. リグレッション資産

- App Serverの版別JSONLフィクスチャ。
- 代表Git状態の小さなリポジトリ群。
- 攻撃的リポジトリ内容。
- 正常・不正Live2Dパック。
- 決定カードのスナップショット。
- reduced motion・高コントラストの画面テスト。
- 大差分・長時間タイムラインデータ。
- サポート出力の正解/不正スキーマ集。

## 14. リリース判定

### 必須

- メインモデル固定が破られない。
- 既存Codex認証を安全に利用。
- サポート履歴非永続化の監査成功。
- 既存Git変更の誤コミットゼロ。
- 構造化質問の安定経路またはフォールバック。
- 三対象OSで基本シナリオ成功。
- reduced motion・キャラクター非表示で全機能利用可能。
- 署名・公証・更新検証。
- Live2D公開ライセンスと同梱資産権利の確認。

### 望ましい

- detached review。
- TTS。
- ユーザーキャラクターインポート。
- 並行worktree。
- 高度な復元分岐。

## 15. データから要件を調整する項目

- 作業単位の既定サイズ。
- 実況頻度。
- キャラクターの画面占有率。
- サポートモデル配分。
- 独立レビューの起動条件。
- 変更予算。
- タイムライン保持期間。
- 音声利用率。
- Linux対応範囲。

これらを好みだけで固定せず、スパイク・ユーザーテスト・実運用データで更新する。
