# 06. 意思決定、信頼較正、擬人化、アクセシビリティ

## 1. 結論

キャラクターを伴うAIコーディング体験では、親しみやすさと過信リスクが同時に増える。本製品は、AIを人間らしく見せること自体を目的にせず、ユーザーが次の状態を素早く理解するためにキャラクターを使う。

- 現在の工程。
- ユーザー入力が必要か。
- 不確実な点があるか。
- リスクが上昇したか。
- 検証が成功したか、未実施か。
- 作業が停滞・逸脱していないか。

Human-AI Interactionのガイドラインは、AIが通常時だけでなく、誤った時や長期利用時にどう振る舞うかを設計する必要性を示している。信頼は最大化するのではなく、能力と限界に合う水準へ較正するべきである。参照: [HCI-01](SOURCES.md#hci-01)、[HCI-04](SOURCES.md#hci-04)

## 2. 三種類の「確からしさ」を分離する

UIでは、少なくとも次を別データとして扱う。

### 2.1 観測された証拠

- テストの成功・失敗。
- 終了コード。
- 型チェック・lint・静的解析。
- 変更ファイル、差分、カバレッジ。
- 再現手順の実行結果。
- 対応OSでの実機確認。

これは最も強い情報である。ただし「全テスト成功」は、テストが十分であることを自動的には意味しない。対象範囲も表示する。

### 2.2 モデルによる自己評価・推定

- 解決策への確信。
- 未知の領域。
- リスクの推定。
- 推奨選択肢。

これは有用な手掛かりだが、校正された確率とは限らない。ラベルを「モデル推定」とし、客観証拠と混ぜない。

### 2.3 演出上の状態

- 考え中。
- 困惑・不確実。
- 注意。
- 安堵。
- 待機。

これは人間が状態を素早く知るための表現であり、モデルの内的感情や正確さを証明しない。

## 3. 信頼較正のUI

### 3.1 推奨する証拠ブロック

```text
検証状態: 部分的
✓ 単体テスト 42件
✓ 型チェック
— Windows実機 未確認
! 認証失敗時の回帰テストなし

モデル推定: 中程度の確信
理由: 既存パターンと一致するが、OS固有コードを含む
```

表情はこのブロックの補助であり、置き換えではない。

### 3.2 不確実性の表示

不確実性は一つの色や顔だけで示さず、次を表示する。

- 何が不明か。
- 不明な理由。
- 追加で得られる証拠。
- 証拠を得るコスト。
- 不明なまま進む場合のリスク。

不確実性可視化の効果は利用者や状況で異なるという研究結果があるため、色・大きさ・透明度だけに依存しない。参照: [HCI-06](SOURCES.md#hci-06)

### 3.3 「自信あり」を成功状態にしない

以下を区別する。

- `confident_unverified`: モデルは自信があるが検証不足。
- `uncertain_verified`: モデルは不確実だが、対象テストは成功。
- `confident_verified`: 推定と証拠が一致。
- `uncertain_failed`: 不確実かつ検証失敗。

キャラクターの成功表現を強くするのは、客観証拠と完了条件が揃った場合に限る。

## 4. 構造化意思決定の設計

### 4.1 質問を分類する

| 種類 | 例 | 必要情報 |
|---|---|---|
| Product | UX、仕様、互換性の優先 | 利用者影響、代替、可逆性 |
| Architecture | ライブラリ、境界、データモデル | 長期コスト、移行、依存 |
| Safety | 削除、権限、ネットワーク | 対象、最悪影響、復元 |
| Quality | テスト追加、範囲縮小 | 未検証領域、時間、欠陥リスク |
| Scope | 作業分割、後回し | 完了条件、依存、レビュー量 |
| Conflict | 既存変更との競合 | 所有者、保持対象、選択肢 |

質問種別により必須フィールドを変える。危険操作には、通常の製品判断より強い確認を要求する。

### 4.2 決定カード

#### ヘッダー

- 一文の問い。
- 緊急度ではなく「ブロックしている工程」。
- 影響レベル。
- 既定で安全な選択肢があるか。

#### 本文

- なぜ今必要か。
- これまでに決まった関連事項。
- 各選択肢の効果、影響、リスク、可逆性、必要作業。
- 推奨と根拠。
- 不足情報。
- 関連差分、テスト、タイムライン。

#### 操作

- 選択。
- 自由入力。
- 詳しく質問する。
- 保留。
- 作業を中断。
- 高リスク時の再確認。

### 4.3 推奨の出所

推奨は次のいずれかを明示する。

- メインコーディングエージェントの推奨。
- サポートセッションによる整理・推奨。
- 決定論的ポリシーによる安全既定。
- プロジェクト設定に基づく既定。

出所を混ぜると、ユーザーは誰の判断か追跡できなくなる。

### 4.4 可逆性

可逆性は単なる真偽ではなく、次の段階で示す。

- `easy`: 一つのコミットを戻せる。
- `moderate`: 追加マイグレーションやデータ変換が必要。
- `hard`: 外部公開API、配布済みデータ、ユーザー生成データへ影響。
- `irreversible`: 削除・外部送信等で完全復元できない。

復元手順がある場合は具体的に示す。

## 5. AIが間違った時の体験

### 5.1 隠さない

失敗した試行をタイムラインから消して「最初から正しかった」ように見せない。表示は要約できるが、次を残す。

- 何を試したか。
- なぜ試したか。
- どう失敗したか。
- 何を学んだか。
- 次に何を変えたか。

### 5.2 謝罪より回復情報

キャラクターが長く感情的に謝るより、次を優先する。

1. 影響範囲。
2. 現在安全か。
3. 変更を戻したか。
4. 次の修正案。
5. ユーザー判断が必要か。

### 5.3 失敗の責任をユーザーへ押し付けない

「あなたが選んだから失敗した」という表現を避ける。決定時に提示した情報、当時の不確実性、新たに得た証拠を比較する。

## 6. 擬人化の安全原則

### 6.1 許容する表現

- 「少し迷っているようです」ではなく、「二案が残っており、判断材料が不足しています」。
- キャラクター設定に沿った口調。
- 継続作業を楽しくする軽いリアクション。
- 状態変化への短い共感的説明。

### 6.2 避ける表現

- AIが感情、意識、欲求を持つと断定する。
- キャラクターへの愛着を使って危険操作を承認させる。
- ユーザーが離席・停止・拒否したことへ罪悪感を与える。
- 「私を信じて」と証拠なしに要求する。
- 人間の同僚や専門家を不要と断定する。
- 親密さを利用してAPIキーや秘密を入力させる。

最近の研究は、人間らしい設計が擬人化を高め、関与と信頼に複雑な影響を与える可能性を示しているが、分野は発展途上である。プロダクト固有のユーザーテストを必要とする。参照: [HCI-07](SOURCES.md#hci-07)

### 6.3 キャラクター設定の境界

キャラクターコンテキストは次を上書きできない。

- 安全ポリシー。
- 承認要件。
- モデル固定。
- プロジェクトの技術制約。
- 事実と証拠。
- ライセンス・プライバシー表示。

「常に自信満々」「危険を軽く扱う」などの設定は、表現ポリシーにより制限する。

## 7. 認知負荷の制御

AIコードレビューに関する研究では、AIの詳細なフィードバックが有用な一方、過剰な量や文脈不足が認知負荷を増やし、人間の理解・テスト・知識移転が依然重要であることが報告されている。参照: [HCI-02](SOURCES.md#hci-02)、[HCI-03](SOURCES.md#hci-03)

### 7.1 Progressive disclosure

- 一行の状態。
- 3〜5行の要約。
- 必要時に詳細。
- 元イベント・ログ・差分へ遡れる。

### 7.2 一度に一つの主要求

質問、承認、レビュー指摘を同時に複数ポップアップしない。優先キューへ集約し、どれが作業を止めているかを示す。

### 7.3 復帰サマリー

一定時間後に戻った時は、次の四区分を既定とする。

- 完了。
- 現在。
- 要確認。
- 次。

長いチャットを上から読み直させない。

## 8. アクセシビリティ要件候補

WCAG 2.2とTauri/WebViewの実装特性を踏まえ、次を要件候補とする。参照: [HCI-05](SOURCES.md#hci-05)

### 8.1 モーション

- `prefers-reduced-motion`を初期値へ反映。
- キャラクターの全モーションを停止可能。
- 停止時も表情の静的切替またはテキスト状態を提供。
- 非本質的な自動モーションを無効化可能。
- 点滅は原則禁止。

### 8.2 キーボード

- プロジェクト一覧、会話、右パネル、質問カードを論理的な順序で移動。
- 選択肢にショートカットを付けても、誤操作しにくい確認を行う。
- ドラッグだけで可能な操作を作らない。
- フォーカスをキャラクターの装飾要素へ奪われない。

### 8.3 スクリーンリーダー

- キャラクターCanvasは装飾として扱い、状態テキストを別要素で提供。
- 工程変化は控えめなlive region。
- コマンド出力の逐次ストリームを自動読み上げしない。
- 質問カードが出た時は、タイトル・影響・選択肢へフォーカスを移す。
- 表情名ではなく意味状態を読み上げる。

### 8.4 色・形・文字

- リスクを色だけで表さない。
- 差分の追加・削除を記号とラベルでも区別。
- テキスト拡大で三領域が破綻しない。
- 高コントラストモード。
- 重要な説明を画像内文字にしない。

### 8.5 音声

- 音声は既定オフ。
- 字幕を常に提供。
- 音量・速度・自動再生・割り込みを制御可能。
- 警告音だけで状態を表さない。

## 9. 意思決定ログ

決定はチャット本文だけでなく、構造化して保存する。

```yaml
decision:
  id: D-0014
  requested_at: timestamp
  resolved_at: timestamp | null
  work_unit_id: W-0007
  question: string
  why_now: string
  options: []
  recommendation_source: main_agent | support_agent | policy | none
  selected_option: string | null
  user_rationale: string | null
  evidence_refs: []
  risk_level: low | medium | high | critical
  reversibility: easy | moderate | hard | irreversible
  supersedes: string | null
  superseded_by: string | null
```

後から方針が変わった場合、古い決定を上書きせず、`superseded_by`で関連付ける。

## 10. 評価実験

### 実験A: 生質問 vs 構造化カード

測定:

- 回答時間。
- 選択肢の意味を正しく説明できる割合。
- 後悔・変更率。
- リスク見落とし。
- 「その他」利用率。

### 実験B: テキスト状態 vs キャラクター＋テキスト

測定:

- 中断後の現在地理解時間。
- 入力待ちの見落とし。
- 作業への楽しさ。
- 気が散る度合い。
- 過信尺度。

### 実験C: 表情のみ vs 表情＋証拠分離

測定:

- テスト未実施時の誤った安心。
- 高リスク判断の確認行動。
- モデル推定と客観証拠の区別。

### 実験D: 実況頻度

- 無し。
- 工程遷移のみ。
- 中頻度。
- 高頻度。

測定: 状況把握、集中阻害、ミュート率、重要通知の認識率。

## 11. 受け入れ基準候補

- キャラクターを完全非表示にしても、すべての判断・レビュー・復元が可能。
- 重要状態は、色・音・表情のいずれか一つだけに依存しない。
- 高リスク操作で、感情的な促し文が表示されない。
- モデル自己評価とテスト証拠が明確に区別される。
- 質問カードはキーボードだけで回答・保留・中断できる。
- reduced motion有効時に、非本質的なモーションが開始しない。
- AIが誤った時、失敗・影響・回復方法を追跡できる。
- 決定が後から覆された場合、変更の連鎖を確認できる。
