# 11. MVP境界、実装順序、Go/No-Goゲート、未決事項

## 1. MVPの狙い

MVPで証明すべきことは、機能の多さではなく次の一本の価値連鎖である。

```text
GPT-5.6 Solと会話して作業を開始
  → 作業状態をキャラクターとタイムラインで理解
  → 構造化された質問へ回答
  → 実装と検証が進む
  → レビュー可能な単位で自動コミット
  → 判断・試行・テストを含むレビュー資料を確認
  → 任意チェックポイントを比較・復元できる
```

この連鎖を安定して示せない機能は、初期スコープから外す。

## 2. 推奨MVPスコープ

### P0: コア成立性

1. Tauri v2 + React + TypeScript + Viteのデスクトップシェル。
2. プロジェクト選択と起動診断。
3. ユーザーインストール済みCodex App Serverへのstdio接続。
4. 既存Codexログインの再利用。
5. メインセッションをGPT-5.6 Solへ固定。
6. 対応思考レベルの取得・変更。
7. メインチャット、計画、コマンド、ファイル変更、差分、エラーの表示。
8. コマンド・ファイル承認UI。
9. 一つの同梱・許諾済みLive2Dキャラクター。
10. 意味状態から表情・モーションへの決定論的マッピング。
11. キャラクター非表示・モーション低減。
12. 作業単位と追記型タイムライン。
13. Gitベースライン、変更所有権、チェックポイントコミット。
14. コミットごとのレビュー資料。
15. チェックポイント一覧・差分・比較。
16. サポートセッション一種以上の`ephemeral`実行と非永続化監査。

### P1: 価値を強める

1. 構造化意思決定カード。
2. ネイティブ質問APIの機能検出とフォールバック。
3. 実況サポート。
4. コミット解説サポート。
5. 高リスク時の独立レビュー。
6. 復帰サマリー。
7. 失敗した試行・方針変更の要約。
8. チェックポイントからのrevert/分岐。
9. サポート利用量プロファイル。

### P2: 公開・権利・運用を確認して追加

1. ユーザー所有Live2Dモデルのインポート。
2. TTS読み上げとリップシンク。
3. 複数作業空間の並行実行。
4. Git worktree自動管理。
5. Git notes・外部形式へのレビュー資料エクスポート。
6. プロジェクト間で共有するキャラクターパック。
7. 外部MCPサーバー管理UI。
8. チーム共有・PR連携。

## 3. MVPで明確に外すもの

- 内蔵ターミナル。
- 手動コミットボタン。
- 任意モデル選択。
- GPT-5.6以外へのフォールバック。
- クラウド同期。
- 複数人の共同編集。
- 汎用Git GUI。
- 拡張機能マーケットプレイス。
- アプリ内ブラウザ。
- 自動push・force push。
- ライセンス未確認のキャラクター共有・配布。
- 完全自律で無制限に作業し続けるモード。

## 4. 推奨実装順序

### Stage 0: リスク除去スパイク

- Codex App Serverの三OS接続。
- Sol固定、思考レベル、承認、差分、レビュー。
- `ephemeral`非永続化監査。
- Live2D SDKの三WebView動作。
- 公開ライセンス・同梱モデル権利の書面確認開始。
- 汚れたGit状態での変更所有権実験。

**終了条件:** 主要な公開ゲートが技術的・契約的に解決可能と判断できる。

### Stage 1: 垂直スライス

- 一プロジェクト、一メインセッション。
- チャットと基本イベント。
- 同梱キャラクター。
- 単純な状態マッピング。
- 一作業単位、一コミット、一レビュー資料。

**終了条件:** 代表シナリオを最初から最後まで通せる。

### Stage 2: 意思決定とサポート

- DecisionPortと構造化カード。
- Presence Interpreter。
- Narrator。
- Checkpoint Curator。
- レート・利用量・停止設定。

**終了条件:** サポート停止時もメインが同じ作業を完了でき、サポート有効時に理解が改善する。

### Stage 3: 品質ハーネス

- Work Unit状態機械。
- 変更予算。
- テスト証拠。
- 既存変更分離。
- 独立レビュー。
- 復元。

**終了条件:** 大きな変更を複数チェックポイントへ安全に分割できる。

### Stage 4: 配布品質

- ネイティブCIマトリクス。
- コード署名・公証。
- アップデーター。
- DBマイグレーション。
- CSP・capability監査。
- 長時間・障害・セキュリティテスト。

**終了条件:** 対象OSへ署名済み成果物を配布し、更新・回復できる。

### Stage 5: 条件付き拡張

- ユーザーモデルインポート。
- TTS。
- 並行worktree。
- 外部連携。

ライセンス・利用量・安全性のゲートを満たした機能だけを有効化する。

## 5. Go/No-Goゲート

### G1. Codex統合

**Go条件**

- 既存ログインでApp Serverを利用できる。
- `gpt-5.6-sol`を検出・固定できる。
- 承認、差分、エラー、レビューを構造化して扱える。
- 最小対応バージョンを決められる。

**No-Go条件**

- 端末出力解析へ依存しないと主要体験が成立しない。
- モデル固定を保証できない。

### G2. サポート履歴隔離

**Go条件**

- `ephemeral`実行で通常のセッション履歴ファイルを生成しない。
- raw入力をアプリDBへ保存しない。
- サポート停止がメインへ影響しない。

**No-Go条件**

- サポート履歴が通常履歴へ混入する。
- ツール・リポジトリ権限を安全に外せない。

### G3. Git安全性

**Go条件**

- 既存変更を誤ってコミットしない。
- 同一ハンク競合で停止。
- コミット前後のクラッシュから回復。
- 復元操作がデータ損失を起こさない。

**No-Go条件**

- 自動コミットの所有権を証明できない。

### G4. Live2D公開条件

**Go条件**

- SDK公開条件を権利者と確認。
- 同梱キャラクターの必要権利を確認。
- ユーザーインポート機能の扱いを文書化。

**No-Go条件**

- Expandable Application該当性・契約が未解決のままインポートを一般公開。

### G5. WebView互換性

**Go条件**

- 対象OSでLive2D、差分、長時間ストリームが安定。
- GPU問題時に静的・非表示へ縮退。
- reduced motionが機能。

**No-Go条件**

- 一OSで高頻度クラッシュ、過大CPU/GPU、入力不能。

### G6. 意思決定UX

**Go条件**

- 生質問より理解度または判断時間が改善。
- 高リスクで過信・感情誘導が増えない。
- キーボード・スクリーンリーダーで操作可能。

**No-Go条件**

- キャラクターが承認率を上げるだけで、理解や安全を下げる。

### G7. 配布と供給網

**Go条件**

- 署名済み成果物。
- macOS公証。
- 更新署名検証。
- SBOM・依存固定・秘密分離。

## 6. 代表シナリオ

MVPの一連の価値を示しやすいシナリオ:

1. ユーザーが既存の小さなTauriプロジェクトを開く。
2. 「設定値を平文ファイルから安全な秘密保管へ移行したい」と依頼。
3. メインセッションが調査計画を提示。
4. キャラクターは調査中状態を示し、工程遷移だけ実況。
5. OS資格情報ストアと暗号化ファイルの選択が必要になる。
6. 意思決定カードが影響、可逆性、クロスOS差を提示。
7. ユーザーが選択。
8. AIが実装・テスト。
9. 一OS固有テストが失敗し、方針変更をタイムラインへ記録。
10. 修正後、検証証拠をまとめる。
11. ハーネスが対象変更だけをコミット。
12. レビュー資料が目的、差分、決定、失敗、テスト、未確認OSを示す。
13. ユーザーが差分コメントを返し、次チェックポイントで修正。

このシナリオは、認証情報、クロスプラットフォーム、意思決定、失敗、レビュー、Gitを一度に検証できる。

## 7. 未決事項

### Codex

- 対応するCodex CLI最小バージョン。
- App Server実験APIの安定化見込みと互換期間。
- サブスクリプション・ワークスペースごとのSol可用性。
- サポートセッションが利用枠へ与える実際の影響。
- `ephemeral`の版別挙動。
- App Serverの同時スレッド数と長時間安定性。
- メインスレッドの永続化・復元UX。

### モデル

- メイン既定思考レベル。
- Luna/Terra/Solの役割別精度・遅延・利用量。
- 高リスクレビューに必要な思考レベル。
- サポートモデル不可時のファミリー内代替ルール。

### Git

- MVPでクリーン作業ツリーを必須にするか。
- worktreeを最初から採用するか。
- commit signingとhookへの対応範囲。
- submodule、LFS、sparse checkoutの対応時期。
- 自動コミット前レビューの既定。
- チェックポイントサイズの初期値。

### Live2D・権利

- Expandable Applicationとしての審査・契約。
- 同梱モデルの再配布・動画・音声連動権利。
- ユーザーインポートの公開条件。
- Core/SDKをソース配布物へ含める可否。
- キャラクター切替時のアセット暗号化・保護要否。
- TTS音声のキャラクター利用条件。

### Tauri・OS

- 初期対応OSとアーキテクチャ。
- Linux対象ディストリビューション。
- Windows WebView2最小バージョン。
- macOS最小バージョン。
- GPU/WebGL性能下限。
- StrongholdとOSネイティブ秘密保管の選択。
- 自動更新の提供時期。

### UX

- 三領域の既定幅。
- キャラクターの既定サイズ。
- 実況頻度。
- 判断カードの必須情報量。
- 高リスク時の二段階確認。
- キャラクターの表現強度。
- 離席・復帰判定を時間だけで行うか。

### データ・プライバシー

- タイムライン保持期間。
- ローカルDB暗号化の必要性。
- レビュー資料のエクスポート形式。
- 診断バンドルの内容。
- 外部テレメトリを持つか。
- プロジェクト削除・アンインストール時のデータ消去。

## 8. 要件定義の推奨順序

1. **権利・公開条件**: Live2D SDKと同梱資産。
2. **信頼境界**: Codex、Git、WebView、サポート、TTS、資産。
3. **セッションモデル**: メイン、通常サブエージェント、サポート。
4. **作業単位とチェックポイント**: 品質ハーネスの正本。
5. **意思決定スキーマ**: 質問・承認・リスク。
6. **タイムラインとデータ保持**。
7. **画面情報アーキテクチャ**。
8. **Live2D意味状態とアクセシビリティ**。
9. **クロスOS配布・署名・更新**。
10. **評価指標とリリースゲート**。

画面一覧から先に要件を作ると、品質・履歴・権限の正本が曖昧になるため、ドメインと信頼境界から始める。

## 9. 要件定義へそのまま移せる主要制約

- メインモデルはGPT-5.6 Sol固定。
- UIにモデル変更を置かない。
- 思考レベルは対応値だけを表示。
- サポートモデルはGPT-5.6ファミリーのみ。
- サポートは通常サブエージェントと分離。
- サポート履歴は通常Codexセッション履歴へ永続化しない。
- サポート利用をユーザーへ開示し、停止可能。
- ターミナルを提供しない。
- 手動コミットボタンを提供しない。
- 自動コミットは作業単位・検証・所有権ゲート後だけ。
- 既存ユーザー変更を自動コミットしない。
- キャラクター表現だけでリスク・成功・不確実性を伝えない。
- キャラクター非表示・モーション停止でも全機能が使える。
- TTSは既定オフ、別APIキー、送信前秘匿化。
- ユーザーモデルインポートは公開ライセンス確認をゲートとする。
- 各OSのネイティブCIでビルド・テスト・署名する。
- 実験的APIは互換アダプターとフォールバックの背後に置く。

## 10. 次工程への入力

要件定義では、各機能について次を明記する。

- ユーザーストーリー。
- 正本データ。
- 信頼境界。
- 前提と対応バージョン。
- 正常フロー。
- 失敗・縮退・復旧フロー。
- 権限と承認。
- 保存・送信・保持。
- アクセシビリティ。
- 観測イベント。
- テスト可能な受け入れ条件。
- 公開ゲート。

「AIが適切に判断する」のような検証不能な文を避け、イベント、スキーマ、ポリシー、証拠、ユーザー操作へ分解する。
