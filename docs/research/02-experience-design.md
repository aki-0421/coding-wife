# 02. 体験設計と情報アーキテクチャ

## 1. 調査方法と抽象化方針

依頼者が指定した参考製品の公開UI、公開ドキュメント、更新履歴を観察し、次の観点へ抽象化した。

- 並行作業を「会話」ではなく「独立した作業空間」として扱う方法。
- チャット、差分、状態、レビューを同時に把握する情報階層。
- 低重要度のエージェント出力を抑え、承認・失敗・完了を目立たせる方法。
- 目標、進捗、利用量、待機状態を常時把握する方法。
- 差分上のフィードバックを、そのままエージェントへ返す方法。

名称、固有のコピー、アイコン、配色、画面資産は調査成果へ含めず、一般化した設計原則だけを採用する。[UX-OBS-01](SOURCES.md#ux-obs-01)

## 2. 参考にすべき抽象パターン

### 2.1 作業空間を委任単位にする

一つのプロジェクト内でも、独立してレビュー・統合できる作業を別の作業空間として扱う。作業空間は次を束ねる。

- Gitブランチまたはワークツリー。
- メインセッション。
- 現在の目標と工程。
- 作業チェックポイント。
- 差分、テスト、リスク、未解決事項。
- プロジェクトコンテキストとキャラクターコンテキスト。

ただし、同一ファイル群を強く共有する作業を無理に分けると、コンフリクトと認知負荷が増える。分割基準は「独立して出荷・レビューできるか」とする。Git worktreeは開発上の分離であり、セキュリティ境界ではない。参照: [GIT-01](SOURCES.md#git-01)

### 2.2 三領域の情報構造

推奨するデスクトップの基本構造は次の通りである。

```text
┌──────────────┬────────────────────────────┬────────────────────────┐
│ プロジェクト  │ 会話・キャラクター           │ 文脈依存パネル           │
│ 作業空間      │ 目標・実況・質問             │ 差分 / 判断 / 検証 / 履歴│
│ 状態一覧      │ メインセッション             │ レビュー資料             │
└──────────────┴────────────────────────────┴────────────────────────┘
```

- **左**: プロジェクト、作業空間、待機、実行中、要確認、失敗、完了、未読。
- **中央**: メイン会話、Live2Dキャラクター、短い実況、現在目標、入力コンポーザー。
- **右**: 現在の文脈に応じて、差分、チェックポイント、意思決定、テスト結果、タイムラインを切り替える。

ターミナルは置かない。コマンドの詳細が必要な場合は、右パネルの「検証証拠」で実行内容、終了コード、要約、展開可能なログとして見せる。

### 2.3 常時表示する目標・状態ヘッダー

中央上部に、少なくとも次を表示する。

- 現在の目標。
- 工程: 調査 / 設計 / 実装 / 検証 / 修正 / レビュー / 入力待ち。
- 進捗: 完了した工程数と残り。
- 現在の注意レベル: 通常 / 注意 / 高リスク / 停止。
- メインモデル: GPT-5.6 Sol固定であること。
- 思考レベル。
- 利用量または利用制限に関する取得可能な状態。
- 停止・中断操作。

モデル選択UIは表示しない。モデルが利用できない場合は、別モデルへ黙って切り替えず、開始を止めて理由と解決方法を示す。

### 2.4 低重要度イベントの折りたたみ

エージェントの全活動を同じ強さで並べると、重要な質問が埋もれる。表示層を分ける。

| 層 | 例 | 既定表示 |
|---|---|---|
| Action | ユーザー判断、危険操作承認、テスト失敗、リスク上昇 | 展開して固定 |
| Milestone | 工程開始・完了、コミット、レビュー完成 | 要約表示 |
| Activity | 調査対象、実行コマンド、ファイル変更 | グループ化 |
| Telemetry | ストリーム断片、内部デバッグ、頻繁な状態更新 | 非表示または開発モード |

同じエラーの繰り返しや連続コマンドは、一つの「試行」にまとめる。ただし、監査用の元イベントはローカルタイムラインへ保持できる。

## 3. 中央領域: キャラクターと会話

### 3.1 キャラクターの位置づけ

キャラクターは会話領域に存在するが、常に最大表示する必要はない。

- 通常会話: 中央の主要な視覚要素。
- 長い差分レビュー: 小さなドック表示へ退避。
- 高リスク判断: キャラクターの演出を抑え、選択肢と証拠を優先。
- ユーザー入力中: 視線や待機モーションは控えめにする。
- 画面幅が狭い場合: キャラクターを折りたたみ、状態アイコンと字幕を残す。

### 3.2 キャラクターが伝える状態

推奨する意味層は、感情語よりも運用状態である。

| 意味 | 表現例 | 必須の非視覚表現 |
|---|---|---|
| 集中・処理中 | 視線、軽い待機モーション | 「実装中」状態ラベル |
| 不確実 | 困惑寄りの表情 | 不確実な点と不足証拠 |
| 注意 | 緊張した表情、短い合図 | リスクカード |
| 入力待ち | ユーザーを見る | 質問カード、通知 |
| 検証成功 | 控えめな肯定モーション | テスト結果と対象範囲 |
| 失敗・停滞 | 落ち着いた注意表現 | エラー要約、試行数、次案 |

「喜んでいるから安全」「自信がありそうだから正しい」という誤解を防ぐため、表情と検証状態を別々のデータとして扱う。

### 3.3 実況の設計

実況はトークンの逐次読み上げではなく、意味のある状態遷移の短い説明である。

良い例:

- 「認証処理の呼び出し箇所を三つ確認しています。」
- 「実装は完了しましたが、Windows向けテストが一件失敗しています。」
- 「二つの修正案があり、互換性を優先するか変更量を抑えるか判断が必要です。」

避ける例:

- 内部推論の逐語的な再現。
- ソースコードや秘密をそのまま読み上げること。
- 数秒ごとの細かい作業報告。
- 証拠がないのに「問題ありません」と断定すること。

実況にはレート制限、重複抑制、優先度、字幕履歴、完全無効化を設ける。音声は既定でオフにする。

## 4. 構造化意思決定UI

### 4.1 カードの最低スキーマ

```yaml
decision_id: string
title: string
why_now: string
context_summary: string
options:
  - id: string
    label: string
    effect: string
    affected_scope: string[]
    risks: string[]
    reversible: boolean
    rollback: string | null
recommendation:
  option_id: string | null
  rationale: string
  evidence_refs: string[]
uncertainty:
  level: low | medium | high | unknown
  missing_information: string[]
allow_other: true
safe_default: string | null
```

### 4.2 表示順序

1. 一文の質問。
2. なぜ今必要か。
3. 推奨がある場合は、その推奨と根拠。
4. 選択肢の比較。
5. 影響範囲、リスク、可逆性。
6. 詳細ログ・差分・関連判断へのリンク。
7. 自由入力、再質問、保留、中断。

モデルの推奨を強調しすぎない。破壊的・不可逆な選択肢は、キャラクターの魅力や緊急感で誘導せず、明確な警告と追加確認を行う。

### 4.3 質問の演出

キャラクターの吹き出しは質問の導入に使えるが、実際の選択肢は標準UI部品として表示する。キーボード操作、スクリーンリーダー、フォーカス順、選択状態を保証する。自動タイムアウトによる承認は既定で無効にする。Codex側にタイムアウト情報がある場合も、ホストアプリが安全側へ解決する。

## 5. 右領域: レビューと履歴

### 5.1 差分ビュー

差分は次の切り口を切り替えられるようにする。

- 現在のターン。
- 現在の作業単位。
- 特定チェックポイントまたはコミット。
- ベースブランチからの累積。
- ファイル別。

各ファイルで、意図しない変更、テスト不足、ドキュメント不足、生成物、バイナリ、大規模置換を目立たせる。インラインコメントは、次のメインターンに構造化されたフィードバックとして渡す。

### 5.2 チェックポイントカード

カードには次を表示する。

- 目的と完了条件。
- コミットSHA。
- 変更ファイルと行数。
- 主要判断。
- 実行したテストと結果。
- 未解決事項。
- リスクと影響範囲。
- 復元・比較・再レビュー操作。

### 5.3 タイムライン

タイムラインはチャット履歴ではなく、作業の因果関係を示す。

```text
目標設定
  ├─ 調査: 認証フローを確認
  ├─ 判断 D-014: 保存方式を選択
  ├─ 試行 A-022: 方式X → テスト失敗
  ├─ 方針変更 D-015: 方式Yへ変更
  ├─ 検証 T-031: 全対象成功
  └─ チェックポイント C-008 / commit abc123
```

チャットの文面を読まなくても、何が起きたかを追えることを目標にする。

## 6. 左領域: プロジェクト・作業空間一覧

各項目は、名称だけでなく状態を示す。

- 実行中。
- ユーザー入力待ち。
- 承認待ち。
- テスト失敗。
- レビュー可能。
- 高リスク。
- 完了。
- アーカイブ。

未読数より、**介入が必要か**を優先する。並行作業が増えた場合は、全件のアニメーションを動かさず、要注意項目だけを通知する。

## 7. 設定の情報設計

### 7.1 プロジェクトコンテキスト

メインセッションで利用する技術・方針。

- 技術スタック。
- ビルド・テストコマンド。
- コーディング規約。
- 触れてはいけない領域。
- 完了条件。
- リポジトリ固有の指示ファイルとの優先順位。

### 7.2 キャラクターコンテキスト

サポートセッションと演出で利用する設定。

- 話し方、呼び名、口調。
- 実況頻度。
- 感情表現の強さ。
- 禁止表現。
- 表情・モーションの意味マッピング。
- 音声利用と声。

この二つを分離し、キャラクター設定がコーディング判断や安全ポリシーを上書きしないようにする。

### 7.3 アクセシビリティ

- キャラクター非表示。
- モーション停止。
- OSの`prefers-reduced-motion`尊重。
- 表情強度の低減。
- 音声ミュートと字幕。
- 高コントラスト。
- キーボードのみで全判断を完了。
- 状態変化をARIA live region等で通知する際の過剰読み上げ防止。
- キャラクターが点滅・激しい揺れ・長時間の自動移動をしない。

WCAG 2.2では、相互作用に起因する非本質的なモーションを無効化できること、点滅を制限すること、意味のあるフォーカス順を維持することが示されている。参照: [HCI-05](SOURCES.md#hci-05)

## 8. 避けるべきUIパターン

1. キャラクターが差分や質問を覆う。
2. 「悲しませたくない」などの感情的圧力で承認を促す。
3. 表情だけで安全・危険を表す。
4. 長い思考ログをそのまま実況する。
5. すべてのサポート出力を別人格の発言として表示する。
6. モデル選択を隠しつつ、内部で別世代モデルへフォールバックする。
7. 自動コミットを無表示で行う。
8. 失敗した試行を消して、一直線に成功したように見せる。
9. 「完了」と「テスト済み」を同じ状態にする。
10. 参考製品のビジュアルや文言を模倣し、独自のキャラクター中心体験と衝突させる。

## 9. 体験の代表フロー

```text
プロジェクトを開く
  ↓
Codex / Git / モデル / ライセンス済みキャラクターの事前診断
  ↓
目標を会話で設定
  ↓
AIが調査計画を提示
  ↓
工程状態と短い実況を表示
  ↓
判断が必要 → キャラクターが導入 → 構造化カードで回答
  ↓
実装・検証 → 差分と証拠を逐次集約
  ↓
作業単位完成 → 自動コミット → レビュー資料生成
  ↓
ユーザーが差分・判断・失敗・テストを確認
  ↓
次の単位へ進む / 修正を返す / 任意時点へ戻る
```

## 10. 要件化時の確認項目

- 三領域を固定するか、画面幅に応じて二領域へ畳むか。
- キャラクターの既定占有率と、レビュー時の自動退避条件。
- 実況の最大頻度と、重要度ルール。
- 意思決定カードに必須とするフィールド。
- 高リスク領域の追加確認ルール。
- タイムラインに保存する元ログと要約の範囲。
- 差分コメントをメインセッションへ渡すタイミング。
- チェックポイントを自動で次へ進めるか、レビュー待ちにするか。
