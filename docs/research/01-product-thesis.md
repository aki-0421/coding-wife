# 01. プロダクト仮説と問題構造

## 1. 調査結論

本製品の中心価値は「AIと会話しながらコードを書くこと」そのものではない。価値の中心は、AIが大量の作業を進める際に発生する次の三つの負担を減らすことである。

1. **意思決定負担**: 質問の意図、選択肢の違い、影響範囲、可逆性をユーザーが毎回解読する負担。
2. **状況把握負担**: AIが今どの工程にいて、何を試し、何が失敗し、何を不確実と見ているかを追う負担。
3. **レビュー負担**: 巨大な最終差分を一括で読み、設計意図と検証結果を後から復元する負担。

したがって、プロダクトの主語は「コード生成」ではなく、**人間がAIの作業を理解し、介入し、監督し、戻せる状態を維持すること**である。

## 2. 問題の因果構造

```text
AIの実装能力・連続稼働時間が向上
        ↓
一度に変更できる量と速度が増加
        ↓
人間がコードを書く時間は減る
        ↓
一方で、判断要求・監督・レビュー・復元の量が増える
        ↓
最終差分だけを見る運用では理解が追いつかない
        ↓
誤方向の発見が遅れ、差し戻しコストが増える
```

本製品はこの連鎖を、次の逆向きの仕組みで崩す。

```text
作業をレビュー可能な単位へ分割
        +
判断・試行・失敗・検証を時系列に保存
        +
質問を構造化し、リスクと可逆性を明示
        +
状態をテキスト・証拠・キャラクター表現で多重化
        ↓
人間が早い段階で理解・介入できる
        ↓
速度を維持しながら、変更量当たりの監督可能性を上げる
```

## 3. 主要なJob-to-be-Done

### JTBD-A: AIへ大きな作業を任せながら、現在地を見失わない

ユーザーは、別画面を見ている間も、AIが調査中か、実装中か、テスト失敗に対処中か、入力待ちかを把握したい。常時読み上げではなく、工程遷移やリスク上昇など意味のある変化だけを短く通知する必要がある。

### JTBD-B: 判断要求を短時間で理解し、安全に選ぶ

質問カードには、最低限、質問の要約、なぜ今必要か、選択肢ごとの効果、影響範囲、リスク、可逆性、推奨とその根拠、「その他」の自由入力を含める。モデルの推奨と、テスト・静的解析などの客観的証拠は分離して表示する。

### JTBD-C: 巨大な変更を、意味のある単位でレビューする

ユーザーは、ファイル数ではなく、目的単位で変更を読みたい。各チェックポイントに、目的、差分、判断、試行、テスト、未解決事項、復元方法をまとめ、次の単位へ進む前または後に確認できるようにする。

### JTBD-D: AIの作業を任意時点から理解・復元する

「戻る」は、単純なGit resetだけでは不十分である。どの決定に戻るのか、そこから派生したコミットや後続判断が何か、復元後に再実行すべき検証は何かを示す必要がある。

### JTBD-E: 好きなキャラクターとの共同作業を楽しみつつ、能力を過信しない

キャラクターは継続性と親しみを提供するが、AIが本当に感情を持つかのように断定しない。表情は運用状態を補助的に伝え、重要判断ではキャラクター演出よりも証拠と選択肢を前面に出す。

## 4. プロダクト原則

### P1. Evidence before emotion

表情や台詞より先に、差分、テスト、失敗回数、承認要求、変更範囲などの観測事実を保持する。感情表現は、その事実を分かりやすくする補助チャネルである。

### P2. Checkpoints, not a final dump

最終成果物の一括提示を避け、設計・実装・検証などの境界で成果を確定する。チェックポイントは小さすぎてノイズにならず、大きすぎてレビュー不能にならない「意味のある作業単位」にする。

### P3. Decisions are first-class artifacts

質問と回答を一時的なチャットとして消費せず、決定ID、選択肢、選択理由、影響範囲、後から覆されたかをタイムライン上の一級データとして扱う。

### P4. Local control, explicit external use

Git、ファイル、タイムライン、キャラクター資産はローカルを正本とする。一方、Codexと任意の音声生成は外部モデルを利用するため、送信範囲・利用量・有効状態を明示する。「ローカルアプリ」と「完全オフライン」を混同しない。

### P5. Deterministic policy around probabilistic agents

モデルは提案・要約・分類を行えるが、モデル固定、アクセス可能パス、コミット対象、危険操作の承認、秘密の除外、キャラクター資産IDの許可は決定論的なポリシー層が制御する。参照: [SEC-02](SOURCES.md#sec-02)、[SEC-03](SOURCES.md#sec-03)

### P6. User reversibility

承認、コミット、設定変更、キャラクター動作には、可能な限り取り消し・復元・再評価を用意する。取り消せない操作は、実行前に明示する。

### P7. Quiet by default, salient when needed

すべてのトークンやコマンドを実況すると認知負荷が増える。通常は低重要度イベントをまとめ、工程遷移、失敗、リスク、承認待ち、チェックポイント完成だけを浮上させる。

### P8. One coding identity, multiple support roles

ユーザーが会話するコーディングパートナーは一貫してGPT-5.6 Solである。補助処理が複数モデルで動いても、別人格が会話へ割り込むように見せない。サポート出力はメインキャラクターの演出・説明として統合し、出所は必要に応じて詳細画面で確認できる。

## 5. 対象ユーザーの仮説

### 主対象

- Codex CLIを既に利用し、長時間または大規模なエージェント作業を行う個人開発者。
- 実装速度は上がったが、レビューと意思決定がボトルネックになっている利用者。
- キャラクター表現に価値を感じるが、単なるチャットマスコットではなく実務上の有用性を求める利用者。

### 次対象

- AI生成コードをレビューするテックリード。
- 作業過程と判断理由を後から監査したい小規模チーム。
- 音声や視覚的な進捗通知によって、マルチタスク時の状況把握を改善したい利用者。

### 初期対象外

- 完全オフライン環境のみで完結したい利用者。
- Gitを使わないプロジェクト。
- ブラウザだけで使うクラウドIDE。
- 複数人のリアルタイム共同編集を主目的とするチーム。
- あらゆるモデルやエージェントプロバイダーを切り替えたい利用者。

## 6. 機能ではなく価値で見た差別化

| 一般的なAIエディターの中心 | 本製品が中心に置くもの |
|---|---|
| コード生成速度 | 変更の理解速度 |
| チャット履歴 | 判断・証拠・チェックポイントのタイムライン |
| 最終差分 | 工程ごとのレビュー可能な差分 |
| テキストによる状態表示 | テキスト、証拠、キャラクター状態の多重表現 |
| 端末とGit操作の統合 | AIが作業し、人間は判断・レビューへ集中するUI |
| モデル選択の自由 | 一貫したメインモデルと、目的別の裏側最適化 |

## 7. 「ターミナルなし」「コミットボタンなし」の意味

これは単なるUI削減ではなく、責務の再定義である。

- ターミナルを表示しない代わりに、実行したコマンド、終了コード、要約、重要ログ、再現方法をタイムラインと検証パネルで提示する。
- コミットボタンを置かない代わりに、作業単位の完了条件をハーネスが判定し、コミット前後の状態を明示する。
- ユーザーがGitや端末へ逃げないと何も分からないUIにしてはいけない。
- 自動化は不可視化を意味しない。コミット発生、対象差分、コミットSHA、復元方法を必ず表示する。

## 8. 非目標

1. 汎用コードエディターの全機能を再実装すること。
2. 端末エミュレーターを内蔵すること。
3. Git GUIの全操作を提供すること。
4. モデルを自由に選べるマルチプロバイダー基盤を作ること。
5. キャラクターをAIの正確さの保証として扱うこと。
6. サポートセッションの存在や利用量をユーザーから秘匿すること。
7. リポジトリ内の既存変更をAIの成果として勝手にコミットすること。
8. 公開ライセンスが未確認のまま、任意Live2Dモデルの読み込みを一般配布すること。

## 9. 成功仮説

### 仮説H1: 構造化された質問は判断時間を短縮する

生のチャット質問と比較し、ユーザーが選択肢の影響・リスク・可逆性を正しく説明できる割合が上がり、回答までの時間が短くなる。

### 仮説H2: チェックポイントはレビュー漏れと差し戻し範囲を減らす

同じ変更量でも、一括最終差分より、目的ごとのチェックポイントとレビュー資料を使った方が、欠陥発見率と判断理由の再現率が上がる。

### 仮説H3: 状態を表すキャラクターは中断後の復帰を速める

テキストだけの進捗表示と比べ、キャラクター＋短い実況＋状態ヘッダーにより、別画面から戻ったユーザーが現在地を説明できるまでの時間が短くなる。

### 仮説H4: 表情と客観証拠を分離すると過信を抑えられる

「自信あり」の表情だけを出す設計より、モデル推定と検証証拠を別に表示する設計の方が、不十分なテスト結果に対する過信が減る。

## 10. 要件定義前に確定すべき判断

- 初期対応OSの優先順位。
- Gitの汚れた作業ツリーを許可するか、隔離ワークツリーを既定にするか。
- メインセッションの既定思考レベル。
- サポートセッションの利用上限と、完全無効化設定。
- チェックポイントを自動確定する条件と、ユーザー確認が必要な高リスク領域。
- 同梱キャラクターの再配布、動画、スクリーンショット、改変、音声連動に関する権利範囲。
- ユーザーモデル読み込み機能の公開可否。
- ローカルタイムラインの保持期間、暗号化、エクスポート仕様。
