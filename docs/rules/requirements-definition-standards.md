# 要件定義基準

## 目的

記述者、仕様責任者、実装担当、レビュアーが同じ記述から同じ解釈へ到達し、実装後の認識違いを減らす。

すべてを事前に決めることは求めない。決めた内容は一意にし、決めていない内容は未確定事項として明示する。

## 基本原則

1. 決めた内容は、読み手によって解釈が変わらない状態にする。
2. 決めていない内容を空欄や推測で埋めない。
3. スコープは「含める」と「含めない・その理由」の両方を書く。
4. 各機能要件に一意な要件IDを付ける。
5. 1つの要件には、独立して合否を判定できる1つの振る舞いを書く。
6. 各要件に検証可能な受け入れ条件を書く。
7. 正常系だけでなく、異常系、キャンセル、権限差分、空状態、境界値を確認する。
8. デスクトップ固有のライフサイクル、ローカルI/O、OS差分を必要な範囲で定義する。

## 必須項目と着手可の条件

| 区分 | 決めること | 着手可の条件 |
|---|---|---|
| 背景・目的 | なぜ必要で、何を達成するか | 既存の課題と期待する結果が1〜3行で説明できる |
| スコープ | 含める範囲、含めない範囲と理由 | 両方が記載されている |
| アクター・権限 | 利用者と許可する操作 | 全アクターと拒否時動作が特定されている |
| 機能要件 | ユーザーが実現できること | 各要件に一意なIDと受け入れ条件がある |
| 入力 | 項目、必須条件、境界、エラー | フォームがある場合に全入力項目が定義されている |
| デスクトップ固有要件 | OS、終了、ローカルデータ、ネイティブ連携 | 該当領域が定義され、非該当も明記されている |
| 画面・UI | 対象画面IDと対象要件ID | UIを伴う場合は既存または新規画面IDが特定され、伴わない場合は非該当理由がある |
| 非機能要件 | セキュリティ、性能、監査、復旧等 | 該当領域が具体化され、非該当も明記されている |
| 依存・前提 | 外部API、データ、他機能、配布条件 | 未解決依存と着手への影響が分かる |
| 未確定事項 | 決めていない論点 | 確認事項と着手ブロックが判定されている |

## 要件ID

要件IDの形式、維持、廃止は[ID管理ルール](id-management-rules.md)を正本とする。

- 要件定義書は機能単位で `docs/requirements/<feature-name>.md` に置き、要件定義書ごとのサブディレクトリは作成しない。
- 機能ごとに `<PREFIX>-F-NNN` で採番する。
- Prefixは[Prefix・要件定義書台帳](id-management-rules.md#prefix要件定義書台帳)へ先に登録する。
- 要件IDは表示順を表さない。並べ替え後も変更しない。
- 既存要件と独立して合否判定できる振る舞いを追加する場合は、新しい要件IDを発行する。
- 廃止した要件は削除せず、状態、廃止理由、後継要件IDを残す。

## 曖昧さを排除する

次の表現を確定要件へ残さない。具体化できなければ未確定事項へ移す。

| 避ける表現 | 問題 | 是正方法 |
|---|---|---|
| 〜など、〜等 | 対象範囲が閉じない | 対象を列挙する |
| 必要に応じて、適宜 | 実行条件が不明 | 発動条件を書く |
| 原則として、基本的に | 例外が不明 | 例外と例外時動作を書く |
| 適切に、正しく | 合否を判定できない | 観測可能な結果へ置き換える |
| 高速に、大量に、安定して | 数値基準がない | 応答時間、件数、失敗率等を数値化する |
| できるだけ、なるべく | 必須か努力目標か不明 | 必須要件と目標を分ける |

複数条件の組み合わせはデシジョンテーブル、状態変化は状態表または状態図、境界は具体的な数値と含む・含まないで示す。

## 受け入れ条件

受け入れ条件は、その要件が完成したかを判断する合否基準である。次をすべて満たす。

- **検証可能**: 実際の操作や観測によって合否を判断できる。
- **単一**: 1つの条件は1つの結果だけを表す。
- **観測可能**: 表示、保存結果、ファイル、通知、外部API応答等で結果を確認できる。
- **境界明示**: 数量、期間、ファイルサイズ、権限、OS等の境界が明確である。

内部の関数名、React state、Rust struct等を受け入れ条件にしない。利用者または外部境界から観測できる結果を書く。

| 良い例 | 悪い例 | 問題 |
|---|---|---|
| 保存先を選択して保存すると、指定した場所にファイルが作成され、完了表示が出る | ファイルを適切に保存する | 保存先、結果、表示が不明 |
| ファイル選択をキャンセルすると、画面を維持し、エラーを表示しない | キャンセルを考慮する | 観測可能な動作がない |
| 書き込み権限がない場合、入力内容を保持して保存失敗を表示する | 保存に失敗したらエラーにする | データ保持と表示が不明 |

## デスクトップ固有要件

Webアプリの画面要件だけでは不足するため、各機能で次を確認する。共通動作は[デスクトップ共通仕様](../screen-design/desktop-common-specification.md)を参照し、要件定義書には機能固有の契約または共通仕様との差分だけを書く。

| 領域 | 確認すること |
|---|---|
| 対象OS | 対応OS、最低バージョン、OS差分 |
| ウィンドウ | 表示先、生成・再利用、閉じる、再表示 |
| アプリ終了 | 未保存データ、バックグラウンド処理、終了確認 |
| ローカルデータ | 正本、保存先、破損・移行・復元 |
| オフライン | 利用可能範囲、同期、競合、再試行 |
| ファイル・OS操作 | 選択、保存、キャンセル、権限不足、I/O失敗 |
| メニュー・ショートカット | OS差分、有効条件、競合 |
| Deep Link・ファイル関連付け | 起動済み・未起動時の動作、不正入力 |
| Capability・認可 | 必要なネイティブ操作、scope、Rust側認可 |
| アップデート | 互換性、移行、失敗時復旧 |

機能に該当しない領域は空欄にせず「非該当」とする。未検討を非該当扱いにしない。

## React / ViteとTauriの境界

標準構成では、ViteがReact + TypeScriptの静的アセットをビルドし、Tauri v2がWebViewへバンドルする。リリース版でフロントエンド開発サーバーを動作させない。要件定義では次の境界を混同しない。

| 境界 | 主な責務 |
|---|---|
| React WebView | 表示、入力、画面内状態、画面遷移 |
| Vite | React + TypeScriptのビルドと静的アセット生成。実行時の信頼境界にはしない |
| Tauri Command / Rust | ローカルOS操作、信頼境界、必要な認可、長時間処理の調停 |
| Tauri plugin | ファイルダイアログ、通知等の許可されたネイティブ機能 |
| 外部API | サーバー上の正本、共有データ、オンライン処理 |

これは実装を固定する表ではない。ユーザーから見える動作を要件として定義し、具体的なCommand名やplugin構成は画面設計または詳細設計で決める。

## 画面との関係

- 要件定義書の「画面・UI」に、画面IDと対象要件IDを書く。
- 画面詳細仕様の「関連要件」に、要件IDを書く。
- 画面レイアウト、表示状態、操作フローは画面詳細仕様を正本とする。
- 要件定義書へ画面仕様を複製しない。
- 中央集約型のトレーサビリティマトリクスは作成しない。

## 未確定事項

決めていない論点は次の形式で残す。

| 列 | 内容 |
|---|---|
| 論点 | 何が決まっていないか |
| 初期判断 | 暫定方針。なければ「なし」 |
| 確認事項 | 誰に何を確認すれば確定するか |
| 着手ブロック | `はい`、`いいえ`、`不明` |

| 値 | 着手可否 |
|---|---|
| はい | 確定するかスコープから外すまで着手しない |
| いいえ | 着手と並行して確定できる |
| 不明 | 安全側でブロック扱いにする |

## レビューと合意

| 対象 | 作成 | 合意 | 確認・助言 |
|---|---|---|---|
| 背景、目的、スコープ | 記述者 | 仕様責任者 | 実装担当 |
| 機能要件、受け入れ条件 | 記述者 | 仕様責任者 | 実装担当、QA |
| デスクトップ固有要件 | 記述者、実装担当 | 仕様責任者 | QA |
| 未確定事項のブロック判定 | 記述者 | 仕様責任者 | 実装担当 |

仕様責任者による合意前の文書は `Draft` とする。合意後に `Approved` へ変更する。

## 着手可判定

次をすべて満たしたとき、その機能を着手可とする。

- [ ] 背景と目的が説明できる。
- [ ] スコープ内・外と非対象理由が明確である。
- [ ] 全機能要件に一意な要件IDがある。
- [ ] 全機能要件に検証可能な受け入れ条件がある。
- [ ] 正常系、異常系、キャンセル、権限差分、空状態、境界値を確認した。
- [ ] デスクトップ固有要件が定義され、非該当も明記されている。
- [ ] UIを伴う要件では対象画面IDが特定され、伴わない要件では非該当理由がある。
- [ ] 着手ブロックが「はい」または「不明」の未確定事項がない。
- [ ] 仕様責任者がレビューし、合意している。

## 変更フロー

1. 要件定義書を `Draft` として作成または変更する。
2. 関連する画面詳細仕様、デスクトップ共通仕様を更新する。
3. 本基準で着手可否を確認する。
4. 仕様責任者がレビューし、合意後に `Approved` とする。
5. Approvedの文書を正として実装する。
6. 実装中に要件の誤りが判明した場合は、理由を記録して文書を再度レビューする。
